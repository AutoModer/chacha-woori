## 1. 방향 결정

- **아이디어를 계속 다듬는다** (다른 아이디어로 바꾸지 않음).
- 화면 UI가 거의 없다는 점은 약점이 아니라 콘셉트("운전 중 화면을 보지 않게 한다")와 맞는 것으로 본다. PT에서는 "같은 상황에서 기존 내비 음성 vs 이 앱"을 나란히 비교하는 연출로 보완한다.

## 2. 콘셉트 정리

### 2-1. "내비 옵션 하나 아니냐"에 대한 답
- **정보 안내와 행동 신호를 분리한다.** 내비 음성은 사고 다발, 야생동물, 급커브, 단속 카메라, 제한 속도 등을 모두 같은 목소리로 안내한다. 그래서 운전자는 "단순 정보인지, 지금 주행을 바꿔야 하는지"를 구분하지 못하고, 음악을 켜면 귀찮은 안내가 된다.
- 이 앱은 **"이 신호가 나면 핸들을 움직여야 한다"는 전용 채널**을 만든다. 기능 하나를 더하는 게 아니라 안내 체계를 다시 설계하는 것이다.
- 형식: Pleos App Market용 **별도 앱**. NaviHelper로 순정 내비 정보를 읽어 그 위에 판단 로직을 얹는 **"내비 위에 얹는 판단 레이어"**로 설명한다.

### 2-2. 사용자 전제 (통계로 확인 필요)
- 스마트 크루즈 때문에 멍해지는 운전자가 늘었다. → 학계의 자동화 안주(automation complacency) 연구, IIHS 등 운전자 보조 기능 사용 시 주의 저하 연구를 근거로 찾아야 함.
- 고속도로 여부는 내비가 이미 판단하므로 고속도로에서는 기본 동작하도록 설정할 수 있다.

### 2-3. 콘셉트의 두 기둥과 현재 상태

| 기둥 | 상태 |
|---|---|
| ① 결정적인 순간에만 개입한다 | **유지·강화.** 크루즈 상태 등 판단 근거가 생김 |
| ② 음성과 다른 형태(몸)로 알린다 | **약해짐.** 시트 진동 API가 없어 신호음만 남으면 "음성을 못 알아듣는 사람에게 또 소리를 낸다"는 반문 가능 |

- 신호음이 음성과 다른 점: 말이 아니라서 해석이 필요 없음, 방향(좌우 스피커) 표시 가능(실험 필요), 음악을 줄이지 않고 짧게 얹힘.
- 기둥 ②를 살릴 핵심 수단은 **앰비언트 조명**(3장). 조명 제어 동작 여부에 따라 콘셉트가 갈린다.

| 에뮬레이터에서 조명 제어 결과 | 콘셉트 |
|---|---|
| 동작함 | **"빛 + 방향 신호음으로 몸에 알린다."** 원안이 거의 유지됨. 시트 진동은 확장 제안 |
| 동작 안 함 | **"행동 신호를 정보 안내에서 분리한다."** 출력은 방향 신호음, 조명·진동은 API가 열리면 붙는 구조로 설명 |

## 3. 앰비언트 조명

- 차 실내 분위기용 간접 조명. 대시보드 LED 줄, 도어 안쪽, 센터 콘솔, 발밑 등에 있음. 색·밝기 변경, 드라이브 모드 연동 기능.
- 이 아이디어에 좋은 점
  - 쳐다보지 않아도 **주변 시야로 느껴짐**
  - Pleos API가 **좌석 구역(`SeatArea`)별**로 색·밝기를 바꿀 수 있어 방향 표시 가능 (우측 출구 → 조수석 쪽)
  - 소리가 아니라 음악·내비 음성과 겹치지 않음
- 한계
  - 낮에는 잘 안 보임 → 신호음과 함께 사용
  - 차종·트림마다 없을 수 있음 → `checkXXXCapabilities`로 확인하고, 없으면 신호음만 사용
- 관련 API: `setAmbientLightBrightness`, `setAmbientLightBrightnessColor`, `setAmbientLightSwitch` (개발자 포털상 Vehicle Control 계열이라 "준비 중"). 깜빡임 API는 없어 앱이 밝기를 반복해서 바꿔야 함.

## 4. SDK 확인 결과 (2026-11-09, Pleos 문서 직접 확인)

### 4-1. 차량에는 카메라가 있지만 SDK가 열어주지 않음
- 현대차는 전방 카메라·레이더로 FCA, LKA, LFA, HDA2(자동 차로 변경)를 구현함. **차량은 차선을 인식하고 있음.**
- Pleos 문서 전체(약 2,000개 경로)에서 "lane"을 검색한 결과, 경고등 타입 외에는 없음. **NaviHelper에도 차로 정보 없음.**
- **현재 몇 차로에 있는지는 어떤 API로도 받을 수 없음.**

### 4-2. 경고등(Telltale) API — ADAS 항목 있음, 퍼미션이 관건
`TelltaleType`에 아래 항목이 있음 (문서에는 이름만 있고 설명 없음, 의미는 현대차 용어 기준 추정)

| 타입 | 추정 의미 |
|---|---|
| `DRIVER_ATTENTION` | 운전자 주의 경고(DAW) |
| `LKA` / `LFA` | 차로 이탈방지 보조 / 차로 유지 보조 |
| `LCA_LEFT`, `LCA_RIGHT` | 차로 변경 보조 좌/우 (HDA2 자동 차로 변경으로 추정) |
| `ELK` | 비상 차로 유지 |
| `FCA` | 전방 충돌방지 보조 |
| `OVER_SPEED` | 과속 |
| `TURN_SIGNAL_LEFT/RIGHT` | 방향지시등 |

- 데이터 구조: `TelltaleData(type, state[ON/OFF/BLINK], color, priority, warningCount)`
- 퍼미션
  - `registerTelltales`, `checkTelltalesCapabilities`: **`PRIVATE_CAR_SAFETY` (보호 수준 `signature|privileged`)** → 일반 서드파티 앱은 받기 어려움
  - `getTelltalesInfo`: 어노테이션은 `CAR_SAFETY`(일반), 본문은 `PRIVATE_CAR_SAFETY`로 **문서 내 표기가 다름**
- → 에뮬레이터에서 직접 호출해서 확인

### 4-3. 크루즈 상태 — 일반 퍼미션으로 사용 가능
- `getCruiseControlState` / `registerCruiseControlState`: **`CAR_DRIVE` (보호 수준 normal)**

| 상태 | 아이디어에서의 의미 |
|---|---|
| `ENABLED` | 켜져 있지만 대기 중 |
| `ACTIVATED` | 동작 중 → 멍해지기 쉬운 상태 |
| `USER_OVERRIDE` | 운전자가 가속 페달로 개입 |
| `SUSPENDED` | 일시 해제(브레이크 등) → 운전자가 운전을 다시 잡음 |
| `FORCED_DEACTIVATION_WARNING` | 시스템 강제 해제 경고 (운전자 반응 아님) |
| `OTHER` | 기타 |

### 4-4. 에뮬레이터
- **Pleos Connect Emulator v2.1.0 = API 34(Android 14) 시스템 이미지**, AVD Form Factor "Automotive", RAM 4GB.
- Android 14에는 AAOS 표준 ADAS 속성(`LANE_DEPARTURE_WARNING_STATE`, `LANE_KEEP_ASSIST_STATE`, `LANE_CENTERING_ASSIST_STATE`, `FORWARD_COLLISION_WARNING_STATE`, `BLIND_SPOT_WARNING_STATE`, `CRUISE_CONTROL_STATE`, `HANDS_ON_DETECTION_*` 등)이 있음. 모두 "켜짐/경고 발생" 수준의 상태값이고 **현재 차로 번호는 없음.** Pleos가 실제 값을 구현했는지는 호출해 봐야 함.
- 핸들을 잡았는지 감지하는 API는 Pleos SDK에 없음 (AAOS `HANDS_ON_DETECTION_*`은 구현 여부 미확인).

### 4-5. 기획서에 쓸 확장 논리
> "차량은 이미 차선을 인식하고 운전자 주의 상태도 판단하고 있다. 현재는 일반 앱 퍼미션으로 내비 경로, 크루즈, 깜빡이, 조향만 사용하고, 경고등·차로 데이터가 열리면 **하드웨어 추가 없이 소프트웨어만으로** 정확도를 높인다."

## 5. 판단 규칙

### 5-1. 입력
- 다음 안내 지점 종류·남은 거리: NaviHelper `onTBTInfo` (`TURN_EXIT_IC_L/R/C` 등)
- 현재 속도: AAOS Car API
- 운전자 반응: 크루즈 상태, 방향지시등, 조향각
- 상황: 크루즈 `ACTIVATED` 지속 시간, 교통 혼잡도

### 5-2. 기준: 남은 시간 = 남은 거리 ÷ 속도
- 같은 1km라도 시속 110km면 약 33초, 시속 60km면 약 60초 → 거리보다 시간 기준이 맞음.

### 5-3. 단계 (숫자는 예시, 근거 확정 필요)

| 단계 | 조건 | 출력 |
|---|---|---|
| 대기 | 남은 시간 > 60초 | 아무것도 안 함 |
| 준비 | 남은 시간 ≈ 60초 | 짧은 신호 한 번 (출구 방향). 이미 맞는 차선에 있어도 "곧 내린다"는 뜻이라 틀린 안내가 아님 |
| 재촉 | 남은 시간 ≈ 30초, 반응 없음 | 남은 시간이 줄수록 빨라지는 반복 신호 |
| 포기 | 남은 시간 < 10초, 반응 없음 | 재촉을 멈추고 "다음 출구로 다시 안내" (무리한 끼어들기 방지) |

### 5-4. 보정 (시점 앞당기기)
- 크루즈 `ACTIVATED`가 오래 지속
- 교통 혼잡
- (확장) `DRIVER_ATTENTION` 경고등을 읽을 수 있을 때

### 5-5. 해제 조건 — **확정**

| 해제 조건 | 세부 기준 |
|---|---|
| 크루즈 해제 | `SUSPENDED`, `USER_OVERRIDE` (`FORCED_DEACTIVATION_WARNING`은 제외) |
| 방향지시등 | **출구 방향만** 인정. **켰다가 바로 끈 경우도 해제** (운전자가 인식했다는 증거) |
| 조향각 변화 | **출구 방향**으로 기준값 이상 (핸들 잡기 감지 API가 없고, 국내 크루즈·HDA는 원래 핸들을 잡아야 하므로 "잡기"가 아니라 "조향 변화"로 판단) |
| 상황 종료 | 출구 통과(TBT 다음 안내 변경), 경로 재탐색, 안내 종료 |

- **한 번 해제되면 그 출구에서는 다시 울리지 않는다.** 다시 울리면 운전자에게 끼어들기를 강요하는 것으로 느껴짐.
- HDA2 자동 차로 변경도 운전자가 깜빡이를 켜서 시작하므로 방향지시등 조건으로 함께 처리됨.

### 5-6. 아직 정할 값
- 준비·재촉·포기 시간 기준의 근거 (차선 하나 옮기는 데 걸리는 시간, 고속도로 출구 예고 표지 간격 2km·1km·500m 등)
- 차선 변경으로 인정할 조향각 기준값 (일반 보정과 구분)
- 준비 신호와 재촉 신호의 구분 방법 (소리, 조명 색·깜빡임)

## 6. 확인할 것

### 6-1. 에뮬레이터에서 직접 호출해서 확인
- [ ] **앰비언트 조명 제어** (콘셉트를 가르는 실험, 1순위)
- [ ] 경고등 API (`getTelltalesInfo`, `registerTelltales`) 퍼미션 통과 여부
- [ ] AAOS 표준 ADAS 속성, `HANDS_ON_DETECTION_*` 값이 나오는지
- [ ] 크루즈 상태 변화가 Virtual Console로 재현되는지
- [ ] NaviHelper TBT 이벤트가 시뮬레이션 주행(`SIMULATION_GUIDING`)으로 나오는지
- [ ] TTS 동작 여부
- [ ] 앱 오디오 좌우 채널 분리 재생이 되는지

### 6-2. 주최 측 문의 (정책이라 호출로 알 수 없음)
- [ ] 주행 중 화면 없이 백그라운드에서 오디오·조명 신호만 내는 앱이 DO 정책상 가능한지
- [ ] 앱 카테고리 (Maps/Navigation 또는 Mobility Services)
- [ ] "준비 중" SDK(조명 제어, TTS)를 시연에 써도 되는지
- 답을 못 받아도 1차 기획서는 "Mobility Services 카테고리, 백그라운드에서 오디오·조명 신호만 출력"으로 가정하고 작성

### 6-3. 근거 수집
- [ ] 고속도로 출구 근처 급차선 변경 사고 통계
- [ ] 크루즈·운전자 보조 사용 시 주의 저하 연구 (automation complacency, IIHS 등)
- [ ] 운전자 설문 (음성 안내를 끄는지, 출구를 놓친 적 있는지)

### 6-4. 아직 비어 있는 것
- [ ] 사업성 논리 (MAU, Retention, 확대 계획)
